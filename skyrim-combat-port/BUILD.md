# Что нужно, чтобы сборка заработала

Короткий ответ: **игру, Creation Kit, xEdit и компиляторы в Git добавлять не нужно и нельзя.** Это локальные
программы и гигабайты чужих файлов, а не исходники проекта. В репозиторий попадают только наши исходники,
конфигурация сборки, версии инструментов и текстовые описания; сами инструменты пользователь ставит у себя.

Сборка сейчас **не выполняется**, потому что ещё не выбран способ реализации. Ниже — что именно требуется
для каждого варианта, что уже подготовлено в репозитории и в каком порядке это включать.

Если непонятно, что такое «способ реализации» и при чём тут Nexus — см. [`docs/how_a_skyrim_mod_works.md`](docs/how_a_skyrim_mod_works.md).

## Три уровня сборки

| Уровень | Что собирается | Что нужно на машине | Нужен ли Git-конфиг | Статус |
|---|---|---|---|---|
| A. Record-only plugin | `.esp`/`.esl` с расами, CombatStyle, perks, шаблонами NPC, leveled lists | Skyrim SE + DLC, Creation Kit или xEdit (SSEEdit) | Да, когда появится исходник | Не начат |
| B. Papyrus | `.pex` скриптов (group gate для волков, реакция на блок, тайминги) | Уровень A + `PapyrusCompiler.exe` + `TESV_Papyrus_Flags.flags` + исходные скрипты игры (`Scripts.zip`/`Scripts/`) | Да: `src/papyrus/` + команда компиляции | Не начат |
| C. SKSE plugin | `.dll` на C++ | Уровень A + SKSE под точный runtime + Visual Studio + запинованный CommonLibSSE-NG + CMake/vcpkg | Да: `src/native/` + `CMakeLists.txt` | Не начат, и не нужен, пока прототип не докажет обратное |

Уровень A не требует запуска игры и компилятора — только редактор плагина. Поэтому первый реальный
артефакт появится раньше, чем Papyrus и тем более C++.

## Чего в Git быть не должно

- `SkyrimSE.exe`, `Skyrim.esm`, `Update.esm`, DLC/CC-плагины, `Data/`, BSA/BA2-архивы, извлечённые игровые ассеты.
- `CreationKit.exe`, `PapyrusCompiler.exe`, `SSEEdit.exe`, `skse64_*.dll`, `Pandora`, `Nemesis`, `FNIS`.
- Папка Mod Organizer/Vortex, профили, сохранения, логи, `Overwrite/`.
- Абсолютные личные пути. Пути задаются локально в `.env` (он в `.gitignore`).

Проверить это можно так: `git check-ignore -v <путь>` и `git status --short` перед каждым коммитом.

## Что уже есть в репозитории

- `.gitignore` — исключает игру, менеджеры модов, готовые сборки (`build/`, `dist/`, `*.pex`, `*.dll`, `*.log`) и локальный `.env`.
- `.gitattributes` — фиксирует LF для исходников и binary для игровых форматов, чтобы diff не ломался.
- `.env.example` — шаблон локальных путей к игре/CK/xEdit/SKSE. Копируется в `.env`, который не коммитится.
- `tools/check_env.py` — проверяет, что реально установлено, читает версию `SkyrimSE.exe` (только на Windows) и печатает отчёт «есть / нет / неизвестно».
- `DEPENDENCIES.md` — таблица выбранных инструментов с точными версиями; заполняется по мере выбора.
- `SETUP.md` — карточка целевой установки и тестового профиля.

Чего в репозитории **намеренно нет**: пустых `src/`, `assets/`, `tests/`, выдуманных версий зависимостей и
скриптов сборки «на будущее». Они появятся вместе с первым настоящим исходником, иначе это мусор, который
придётся переделывать.

## Порядок, в котором сборка становится возможной

1. **Проверить окружение.** Скопировать `.env.example` → `.env`, вписать свои пути, выполнить:
   ```bash
   python tools/check_env.py
   ```
   Отчёт покажет наличие игры, DLC, CK, компилятора Papyrus, xEdit и SKSE. Личные пути в отчёт не
   отправлять: при необходимости заменить их на `<local>`.
2. **Закрыть решение по архитектуре.** По `docs/vertical_slice_feasibility.md` проверить в CK/игре, хватает ли
   record-level механик (CombatStyle, perks, attack data, пакеты) или нужны Papyrus/animation events.
   Результат записать в `STATUS.md`, а не держать в переписке.
3. **Зафиксировать версии.** В `DEPENDENCIES.md` проставить точные версии CK/компилятора/xEdit/SKSE и runtime,
   под который они поставлены. Без этого сборка невоспроизводима.
4. **Добавить первый исходник уровня A** и вместе с ним — способ его сборки (например, `.esp` в текстовой форме
   через выбранный workflow либо проект CK). Только тогда появляется то, что можно назвать сборкой.
5. **Добавлять Papyrus** только для механик, которые не выражаются записями. Команда компиляции фиксируется
   в `BUILD.md` после первой успешной локальной сборки, а не до неё.
6. **Добавлять C++/SKSE** только если прототип показал, что Papyrus и записи не дают нужного результата.

## Команда компиляции Papyrus (проверить локально)

Точные пути зависят от установки; ниже — форма команды, а не проверенный факт:

```powershell
& "C:\путь\к\Papyrus Compiler\PapyrusCompiler.exe" `
  "src\papyrus\MyScript.psc" `
  -f="TESV_Papyrus_Flags.flags" `
  -i="C:\путь\к\Data\Scripts\Source" `
  -o="build\Scripts"
```

После первой успешной сборки заменить эту заготовку фактической командой, версией компилятора и датой.

## Одна команда сборки

Скрипты лежат в `src/papyrus/*.psc`. Сборка и упаковка запускаются одной командой:

```bash
python tools/build.py --name TGCombatPort --version 0.1.0 --plugin build/TGCombatPort.esp
```

Что происходит: линт исходников → поиск компилятора и флагов → компиляция всех `.psc` в `build/stage/Scripts` →
копирование плагина и `assets/` → вызов `tools/package.py` → `dist/TGCombatPort-0.1.0.zip`.

Линт (`tools/papyrus_lint.py`) проверяет парность `Event/EndEvent`, `Function/EndFunction`, `If/EndIf`,
совпадение `ScriptName` с именем файла и отсутствие табов. Это не компилятор: типы и вызовы функций ловит
только `PapyrusCompiler.exe`. Проверить скрипты отдельно: `python tools/papyrus_lint.py src/papyrus`.
Тесты инструментов: `python -m unittest discover -s tests`. Ссылки в документации:
`python tools/check_docs.py`.

Чего команда не делает: не создаёт `.esp` (его собирают в CK/xEdit) и не запускает игру. Если компилятор
не найден, она скажет об этом и завершится с кодом 2 — это нормальный результат на машине без CK.

Сейчас в `src/papyrus/` один скрипт — `TGCP_AnimEventProbe.psc`, пробник animation events для проверки
бандита и волков. Он **ещё не компилировался настоящим компилятором Papyrus**: проверена только обвязка сборки
на заглушке.

## Упаковка в обычный мод

Собранные файлы складываются в `build/stage` (структура папки Data) и упаковываются командой
`python tools/package.py --stage build/stage --name TGCombatPort --version 0.1.0`. На выходе —
`dist/TGCombatPort-0.1.0.zip`, который ставится через MO2/Vortex как любой другой мод. Подробно, вместе с
проверкой установки и публикацией: [`RELEASING.md`](RELEASING.md).

## Что считать результатом

- **Built** — команда сборки завершилась без ошибок и создала файл в `build/`. Артефакт в Git не коммитится.
- **Tested in game** — плагин загружен в отдельном тестовом профиле на известном runtime, сцена пройдена,
  результат и логи добавлены в журнал `STATUS.md`. `Built` не означает `Tested`.
- Пока ни одного из двух не было: в репозитории нет ни исходников плагина, ни выполненной сборки.
